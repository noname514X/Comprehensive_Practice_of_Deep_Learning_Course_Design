# Vibe Coding 记录与反思

## Prompt 记录

### Prompt 1：读取选题指南并选择题目

目标：根据 HTML 指南提取课程要求、评分标准、提交物和 12 个选题，选择一个适合本地完成的题目。  
修正：优先选择不依赖 GPU、能做 Web 界面和可复现实验的题目。最终选择题目 8：端到端智能客服系统。

### Prompt 2：设计工程架构

目标：把客服系统拆成 RAG、意图识别、工具调用、多轮记忆、Web API 和前端界面。  
修正：为了降低依赖风险，要求默认使用 Python 标准库实现，Ollama 只作为可选增强。

### Prompt 3：实现 RAG 检索

目标：实现无需第三方依赖的 TF-IDF 检索，并支持中文问题。  
修正：中文不能只按空格分词，因此加入中文单字、二元词、三元词 token，提高召回能力。

### Prompt 4：实现 Agent 路由与 Function Calling

目标：让系统根据意图调用 query_order、create_ticket、transfer_human 和 compare_products。  
修正：增加订单号、产品、售后动作和情绪抽取，让工具调用参数更完整。

### Prompt 5：补全 Web 界面

目标：做一个真实客服风格的三栏界面，能展示对话、运行统计、工具调用和引用来源。  
修正：避免做成营销落地页，界面保持工具型、可扫描、适合答辩演示。

### Prompt 6：构建测试集和消融实验

目标：根据指南要求补 20 条测试对话，并加入 RAG Top-K 消融实验。  
修正：将评估结果写入 Markdown 报告，便于课程报告直接引用。

### Prompt 7：撰写课程报告和答辩稿

目标：按指南结构写课程设计报告，并给出 2 人分工答辩稿和预测问题。  
修正：成员姓名先用成员 A/B 占位，方便替换为真实姓名。

## 开发反思

Vibe Coding 的优势是能快速把课程要求转成工程结构，并自动补齐 README、报告、评估脚本和答辩材料。尤其在本项目中，AI 能帮助同时考虑“能运行”和“能答辩”两个目标，避免只写代码而忽略实验和讲解。

但 AI 辅助开发不能替代人工判断。比如选题时需要结合本机环境、课程评分点和演示稳定性；RAG 检索用 TF-IDF 还是语义向量，也需要权衡依赖风险；评估结果 100% 也需要人工解释其局限，不能夸大为真实场景表现。最需要人工介入的是业务边界、失败案例分析和答辩时对原理的理解。

比较有效的 Prompt 是把要求写清楚：限制依赖、指定交付物、要求可复现评估、要求保留可解释中间结果。效果较差的 Prompt 是只说“做一个客服系统”，因为它容易变成泛泛聊天机器人，缺少工具调用、记忆和评估。
