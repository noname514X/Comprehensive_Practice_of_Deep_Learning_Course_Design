# 三人分工答辩演讲稿

> 建议总时长 18-22 分钟。成员 A 负责项目背景、RAG 检索与意图路由，成员 B 负责工具调用、记忆系统与功能演示，成员 C 负责实验评估与总结改进。姓名可将"成员 A / B / C"替换为真实姓名。

## 开场与项目概述（成员 A，约 3 分钟）

各位老师好，我们小组选择的是题目 8：端到端智能客服系统。项目叫 SmartCare，场景是电商耳机售后客服。

选这个题是因为它覆盖课程里几乎所有重点模块：词表示、向量检索、RAG、Prompt Engineering、Function Calling、Agent 路由、Memory、结构化输出和工程化评估，而且不依赖 GPU，适合本地稳定演示。

我们的目标不是只做一个聊天机器人，而是做一个能跑通业务闭环的客服原型。用户可以查订单、问产品参数、申请退换货、投诉转人工、做多轮追问。系统先识别意图和情绪，再根据不同场景走知识库问答、调用订单工具、创建售后工单，或者转人工。最后我们还做了 Web 界面、SQLite 持久化，以及两套实验评估。

## 系统总体架构（成员 A，约 2 分钟）

系统分为三层。前端是 Web 聊天界面，三栏布局：左侧演示场景按钮，中间聊天窗口，右侧展示意图路由、工具调用 JSON 和 RAG 引用来源。这样老师不仅能看到回答，也能看到系统为什么这样回答。

后端用 Python 标准库实现，入口 `app.py`，核心编排模块 `SmartCareBot`。接到用户消息后，先调意图识别，再根据意图走不同路径：订单走 `query_order`，售后走 `create_ticket`，投诉走 `transfer_human`，产品咨询走 RAG 检索。

数据层包括：`data/knowledge/` 下的 FAQ 和产品文档、`data/orders.json` 模拟订单、以及 SQLite 数据库做历史记录持久化。

## 知识库构建与 RAG 检索（成员 A，约 3 分钟）

接下来讲知识库和 RAG。我们构造了 7 个知识库文件，包括 32 条 FAQ、三款耳机产品说明、售后政策、物流政策和客服流程。系统启动时读取 Markdown，按标题和空行切分知识块，每个块保留来源文件和章节。

用户提问后，系统用 TF-IDF 做向量检索，取 Top-3 相关片段。选 TF-IDF 是为了保证演示环境绝对稳定，无需额外下载模型和依赖，完全可解释、轻量、零网络。为了适配中文，我们混合提取单字、二元词、三元词和英文数字 token，再算余弦相似度。最后把 Top-3 片段拼进 prompt，生成带引用的回答，前端展示来源、章节和分数。

## 意图识别与 Agent 路由（成员 A，约 3 分钟）

智能客服不能所有问题走同一个回答器。我们设计了八类意图：订单查询、退换货、产品咨询、保修、投诉、闲聊、转人工和兜底。系统先识别意图、情绪和关键槽位，再根据路由表选择处理路径。

槽位抽取方面，订单号用正则匹配，售后动作从"退货、退款、换货、维修"中抽取，产品名通过别名表归一化。用规则而不是 LLM，是因为规则方法在自建测试集上稳定可控，每个判断都有明确依据，答辩追问也解释得清。

情绪识别也是重点。当用户说"你们这什么破服务"，系统检测 angry 情绪，先道歉共情，再调 `transfer_human`，优先级 high。这体现了客服系统不能对愤怒用户继续机械追问的安全策略。

以上就是我负责的背景、RAG 和意图路由部分。接下来交给成员 B。

## Function Calling 与工具实现（成员 B，约 3 分钟）

好，我来介绍工具调用和 Memory 系统。我们模拟了四个工具：`query_order` 查物流，`create_ticket` 创建售后工单，`transfer_human` 转人工，`compare_products` 对比产品。

以退换货为例：用户说"订单 2024060112345 的 XX 耳机左耳没声音，我想换货"，系统识别意图为 `return_exchange`，抽取订单号和动作"换货"，调用 `create_ticket`，工单写入 SQLite，回复"已为您创建换货工单"。前端右侧面板展示工具调用 JSON，体现"自然语言 → 结构化参数 → 工具执行 → 自然语言回复"的完整链路。

## Memory 多轮记忆（成员 B，约 2 分钟）

然后是 Memory。真实客服对话往往是多轮的。用户可能先说"查一下订单 2024060112345"，系统返回后再说"那我想换一个"。如果没有记忆，系统就不知道换哪个订单。

我们用 SQLite 存储三张表：`messages` 保存历史消息，`session_state` 保存会话上下文（最近订单号、最近产品、待补充意图、售后动作），`tickets` 保存工单。当用户第一轮提供订单号时，系统写入 `last_order_id`；下一轮用户只说"换一个吧"，系统就能沿用上下文自动创建换货工单。这个设计比只存聊天文本更直接，也更工程化。

## Web 界面与功能演示（成员 B，约 5 分钟）

前端三栏布局：左侧演示场景按钮和运行统计，中间聊天窗口，右侧展示路由、工具调用和引用来源。设计理念是让老师同时看到"用户体验"和"系统内部决策"。

下面我来演示系统。运行 `python3 app.py --port 8000`，访问 `http://127.0.0.1:8000`。

第一个场景查物流。输入"订单号 2024060112345 到哪了？"，系统识别 `order_status`，调用 `query_order`，返回商品、承运方、物流单号和预计送达时间。

第二个场景知识库问答。输入"XX 耳机防水吗？能戴着游泳吗？"，系统走 RAG 检索，回答 XX 支持 IPX4，防汗小雨，不建议游泳，推荐 YY 游泳耳机。右侧引用来源来自 `faq.md` 和 `product_xx_airbuds.md`。

第三个场景退换货。输入"订单 2024060112345 的 XX 耳机左耳没声音，我想换货"，系统创建换货工单并提示客服会联系用户。

第四个场景产品对比。输入"XX 和 YY 有什么区别？"，系统调用 `compare_products`，从价格、防水、续航和场景四个维度对比。

第五个场景情绪投诉。输入"你们这什么破服务，再不处理我就投诉了！"，系统识别 angry 情绪，先道歉，再触发高优先级转人工。

好，演示就到这里。接下来交给成员 C 讲实验评估。

## 实验设计与评估（成员 C，约 4 分钟）

我负责实验评估和总结。我们做了两组实验。

第一组是 20 条测试对话的全面评估。测试集覆盖查物流、缺少参数、退换货、RAG 问答、追问、工具对比、情绪安抚、闲聊和转人工九个场景。运行 `python3 run_evaluation.py` 后，三项指标都是 100.0%：意图识别准确率 100.0%，工具调用正确率 100.0%，RAG 引用命中率 100.0%。这说明在我们定义的业务范围内，系统能稳定完成路由和工具调用。

这里必须坦诚地说明：三个 100% 并不代表系统已经完美。原因有三：

第一，测试集是我们自己构造的，意图标注和工具预期也是我们自己定义的，相当于"自己出题考自己"，天然偏向设计时的场景。第二，意图识别用的是规则匹配，只要测试文本包含了我们预设的关键词和正则，命中率自然高——但真实用户的表达不会这么规整。第三，RAG 引用命中率定义为"检索结果非空即命中"，门槛偏低，无法反映检索质量。

这些指标的真实含义是：**系统在自建封闭测试集上功能完备，逻辑链路闭合**。如果把同样的系统放到真实客服对话中——错别字、口语省略、多意图混合、情绪隐晦表达——这三个数字会明显下降。这也是为什么我们把语义向量模型替换和 LLM 结构化意图识别列为后续改进。

第二组是 RAG Top-K 消融实验。我们标注了 8 个问题的正确资料来源，对比 Top-1、Top-3、Top-5。结果 Top-1 命中率 87.5%，Top-3 和 Top-5 都是 100.0%。所以我们选 Top-3：比 Top-1 更稳，比 Top-5 更精简。

我们还做了有 RAG 和无 RAG 的对比。没有 RAG 时，系统只能用模板回答，"发票丢了还能不能保修"这种问题就缺少依据。加入 RAG 后，每个回答都能追溯到具体来源，对客服系统的可信度至关重要。

## 总结与改进方向（成员 C，约 2 分钟）

最后总结。SmartCare 完成了一个可运行、可演示、可评估的端到端客服原型。它把课程中的多个知识点串成了完整链路：向量检索、RAG 问答、Agent 路由、Function Calling、Memory、情绪识别、评估实验。我们不是单纯调 API，而是把检索、路由、工具和记忆组合成一个能跑业务闭环的系统。

未来改进三个方向：第一，用 BGE 中文向量模型 + ChromaDB 替换 TF-IDF，提升语义召回；第二，用 Qwen2.5 JSON 模式做结构化意图识别，处理多意图和口语表达；第三，接入真实订单和工单后台，增加管理员面板，让系统更接近生产环境。
