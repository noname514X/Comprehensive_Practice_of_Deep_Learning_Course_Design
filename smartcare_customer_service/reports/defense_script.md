# 两人分工答辩演讲稿

> 建议总时长 15-18 分钟。成员 A 负责技术与实验，成员 B 负责系统与演示。姓名可将“成员 A / 成员 B”替换为真实姓名。

## 开场与项目概述（成员 A，约 2 分钟）

各位老师好，我们小组选择的是题目 8：端到端智能客服系统。我们的项目叫 SmartCare，场景是电商耳机售后客服。选择这个题目的原因是它能覆盖课程里多个重点知识：RAG、Prompt Engineering、Function Calling、Agent 路由、Memory 和工程化评估，而且不依赖 GPU，适合在本地稳定演示。

我们的目标不是做一个只能聊天的机器人，而是做一个能完成业务闭环的客服原型。用户可以查订单、问产品参数、申请退换货、投诉转人工，也可以进行多轮追问。系统会先识别用户意图和情绪，再决定是走知识库问答、调用订单工具、创建售后工单，还是转人工。我们还做了 Web 界面、SQLite 历史记录和 20 条测试对话评估。

## 系统架构讲解（成员 B，约 3 分钟）

下面介绍系统架构。我们的系统分为三层：前端交互层、智能编排层和数据工具层。

前端是一个客服聊天界面，中间显示用户和客服的对话，左侧放了几个典型演示场景按钮，右侧展示本轮意图路由、工具调用 JSON 和 RAG 引用来源。这样演示时不只是看到最终回答，也能看到系统内部为什么这样回答。

后端用 Python 标准库实现 HTTP API，入口是 `app.py`。核心模块是 `SmartCareBot`，它接收用户消息后，会调用意图识别模块抽取意图、情绪、订单号、产品和处理动作。然后根据意图选择不同路径：订单问题调用 `query_order`，售后问题调用 `create_ticket`，投诉或人工诉求调用 `transfer_human`，产品和保修问题走 RAG 检索。

数据层包括三部分：第一是 `data/knowledge/` 下的 FAQ、产品说明、售后政策和物流政策；第二是 `data/orders.json` 中的模拟订单；第三是 SQLite，用于保存历史消息、会话状态和工单。这样系统重启后历史记录不会丢失，也符合课程指南里数据持久化的加分要求。

## 核心技术讲解：RAG 与路由（成员 A，约 4 分钟）

接下来讲关键技术。首先是 RAG，也就是检索增强生成。大模型本身不知道我们自定义的耳机价格、防水等级和售后政策，所以不能直接让模型凭空回答。我们把知识库 Markdown 文件按标题和段落切分成知识块，每个知识块保留来源文件和章节。用户提问后，系统用 TF-IDF 向量检索 Top-3 相关片段，再基于这些片段生成回答，并把引用来源展示出来。

这里我们默认使用 TF-IDF，而不是必须下载 Sentence-Transformers，是为了保证演示环境稳定。TF-IDF 的优点是轻量、可解释、无需网络；缺点是语义泛化较弱。为了适配中文，我们没有只按空格分词，而是提取中文单字、二元词、三元词和英文数字 token，再计算余弦相似度。

第二个关键点是 Agent 路由。客服系统不能所有问题都走 RAG。比如“订单号 2024060112345 到哪了”必须调用订单工具；“耳机左耳没声音，我想换货”必须创建工单；“你们这什么破服务”要先安抚并转人工。我们把意图分为订单查询、退换货、产品咨询、保修、投诉、闲聊、转人工和兜底。系统先识别意图和情绪，再选择工具或 RAG 路径。

第三个关键点是 Memory。系统会保存最近订单号、最近产品、待补充意图和售后处理方式。这样用户前一轮说了订单号，后一轮只说“换一个吧”，系统仍能沿用上下文创建换货工单。

## 功能演示（成员 B，约 5 分钟）

下面开始演示。首先运行 `python3 app.py --port 8000`，打开 `http://127.0.0.1:8000`。

第一个场景是查物流。我输入“订单号 2024060112345 到哪了？”。系统识别意图为 `order_status`，调用 `query_order` 工具，返回商品、承运方、物流单号和预计送达时间。右侧可以看到工具调用 JSON。

第二个场景是退换货。我输入“订单 2024060112345 的 XX 耳机左耳没声音，我想换货”。系统识别为 `return_exchange`，抽取订单号和动作“换货”，调用 `create_ticket` 创建售后工单。这里体现了 Function Calling：自然语言被转成结构化参数，再执行工具。

第三个场景是知识库问答。我输入“XX 耳机防水吗？能戴着游泳吗？”。系统走 RAG 检索，回答 XX 支持 IPX4，可以防汗和小雨，但不建议游泳，并推荐 YY 游泳耳机。右侧引用来源显示 `faq.md` 和 `product_xx_airbuds.md`，说明答案来自知识库。

第四个场景是产品对比。我输入“XX 和 YY 两款耳机有什么区别？”。系统调用 `compare_products` 工具，从价格、防水、续航和适合场景四个维度对比。

第五个场景是情绪安抚。我输入“你们这什么破服务，再不处理我就投诉了！”。系统识别 angry 情绪，先道歉共情，再调用 `transfer_human`，优先级是 high。这个场景体现了客服系统的兜底和安全策略。

## 实验结果（成员 A，约 3 分钟）

我们做了两组实验。第一组是 20 条测试对话，覆盖查物流、缺少参数、退换货、RAG 问答、追问、工具对比、情绪安抚、闲聊和转人工。运行 `python3 run_evaluation.py` 后，意图识别准确率为 100.0%，工具调用正确率为 100.0%，RAG 引用命中率为 100.0%。这个结果说明在我们定义的业务范围内，系统可以稳定完成路由和工具调用。

第二组是 RAG Top-K 消融实验。我们标注了 8 个问题的正确资料来源，比较 Top-1、Top-3 和 Top-5。结果是 Top-1 命中率 87.5%，Top-3 和 Top-5 都是 100.0%。因此我们默认选择 Top-3，因为它比 Top-1 更稳，又比 Top-5 更少带入冗余内容。

当然，这个结果不代表真实开放场景也能 100%。目前测试集是自建的，规则意图识别对表达方式仍然敏感。后续可以加入更真实的用户语料，用中文向量模型和 LLM 结构化输出提升泛化能力。

## 总结与改进（成员 B，约 2 分钟）

最后总结一下。SmartCare 完成了端到端客服原型：有 Web 界面，有知识库问答，有订单查询和工单创建，有情绪识别和转人工，也有历史记录和评估脚本。它体现了课程中多个 NLP 和大模型应用知识点，不是单纯调 API，而是把检索、路由、工具和记忆组合成一个完整系统。

未来我们计划做三点改进：第一，用 Sentence-Transformers 或 BGE 中文向量模型替换 TF-IDF，提高语义召回能力；第二，用 Qwen2.5 输出 JSON 做意图识别，处理多意图和口语表达；第三，接入真实订单和工单后台，增加管理员页面，让系统更接近真实生产客服。
