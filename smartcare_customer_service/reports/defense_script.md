# 四人分工答辩演讲稿

> 建议总时长 20-25 分钟。成员 A 负责项目背景与 RAG 检索，成员 B 负责意图识别与工具调用，成员 C 负责记忆系统与功能演示，成员 D 负责实验评估与总结改进。姓名可将"成员 A / B / C / D"替换为真实姓名。

## 开场与项目概述（成员 A，约 3 分钟）

各位老师好，我们小组选择的是题目 8：端到端智能客服系统。我们的项目叫 SmartCare，场景是电商耳机售后客服。

为什么选这个题？因为它能覆盖课程里几乎所有重点知识模块：词表示、向量检索、RAG、Prompt Engineering、Function Calling、Agent 路由、Memory、结构化输出和工程化评估。而且不依赖 GPU，适合在本地稳定演示。

我们的目标不只是做一个能聊天的机器人，而是做一个能跑通业务闭环的客服原型。用户可以查订单、问产品参数、申请退换货、投诉转人工、做多轮追问。系统会先识别意图和情绪，再根据不同场景走知识库问答、调用订单工具、创建售后工单，或者转人工。最后我们还做了 Web 界面、SQLite 历史记录持久化，以及两套实验评估。

## 系统总体架构（成员 A，约 2 分钟）

先看系统架构，分为三层。前端是 Web 聊天界面，中间显示对话，左侧是演示场景按钮，右侧展示意图路由、工具调用 JSON 和 RAG 引用来源。这样老师不仅能看到回答，也能看到系统为什么这样回答。

后端用 Python 标准库实现，入口是 `app.py`，核心编排模块是 `SmartCareBot`。它接到用户消息后，先调意图识别，再根据意图走不同路径：订单走 `query_order`，售后走 `create_ticket`，投诉走 `transfer_human`，产品咨询走 RAG 检索。

数据层分三块：`data/knowledge/` 下的 FAQ 和产品文档、`data/orders.json` 的模拟订单、以及 SQLite 数据库用于持久化历史和会话状态。

## 知识库构建与 RAG 检索（成员 A，约 3 分钟）

接下来讲我们负责的核心部分——知识库和 RAG。

我们构造了 7 个知识库文件，包括 32 条 FAQ、三款耳机产品说明、售后政策、物流政策和客服流程。系统启动时读取 Markdown，按标题和空行切分成知识块，每个块保留来源文件和章节。

用户提问后，系统用 TF-IDF 做向量检索，取 Top-3 相关片段。为什么选 TF-IDF 而不是深度向量模型？因为要保证演示环境绝对稳定，不需要额外下载模型和依赖。TF-IDF 虽然语义泛化弱一些，但完全可解释、轻量、零网络依赖。

为了适配中文，我们没有只按空格分词，而是混合提取单字、二元词、三元词和英文数字 token，然后算余弦相似度。最后把 Top-3 片段拼进 prompt，生成带引用的回答。比如"XX 防水吗"，检索结果来自 `faq.md` 和 `product_xx_airbuds.md`，前端会在右侧展示来源、章节和分数，方便验证答案依据。

以上就是我负责的部分，接下来交给成员 B 介绍意图识别和工具调用。

## 意图识别与 Agent 路由（成员 B，约 3 分钟）

好，感谢成员 A。我来介绍意图识别和 Agent 路由。

智能客服不能所有问题都走同一个回答器。"订单号 2024060112345 到哪了"必须调订单工具，"耳机防水吗"要走知识库，"我要投诉"要安抚然后转人工。所以我们把系统设计成一个轻量 Agent：先识别意图、情绪和关键槽位，再根据路由表选择处理路径。

意图类型一共八类：订单查询、退换货、产品咨询、保修、投诉、闲聊、转人工、兜底。槽位抽取方面，订单号用正则匹配，售后动作从"退货、退款、换货、维修"中抽取，产品名通过别名表归一化，比如"XX耳机""蓝牙耳机"都映射到"XX 蓝牙耳机"。

为什么用规则而不是 LLM？因为规则方法在自建测试集上稳定可控，每一个判断都有明确依据，答辩时老师追问也解释得清。当然我们也知道规则泛化有限，所以报告中已经把 LLM 结构化输出列为后续改进方向。

## Function Calling 与工具实现（成员 B，约 3 分钟）

接下来讲 Function Calling。我们模拟了四个工具：`query_order` 查物流状态，`create_ticket` 创建售后工单，`transfer_human` 转人工，`compare_products` 对比产品。

以退换货为例：用户说"订单 2024060112345 的 XX 耳机左耳没声音，我想换货"，系统先识别意图为 `return_exchange`，抽取订单号和动作"换货"，然后调用 `create_ticket`，生成的工单写入 SQLite，回复用户"已为您创建换货工单"。前端右侧面板会展示工具调用的完整 JSON，体现"自然语言 → 结构化参数 → 工具执行 → 结构化结果 → 自然语言回复"的完整链路。

情绪识别也是我们重点考虑的。当用户说"你们这什么破服务，再不处理我就投诉了"，系统检测到 angry 情绪，先道歉共情，再调用 `transfer_human`，优先级设为 high。这体现了客服系统的兜底策略，不能对愤怒用户继续机械追问。

以上就是我负责的意图路由和工具部分。接下来交给成员 C 做功能演示。

## Memory 多轮记忆与持久化（成员 C，约 2 分钟）

好的，我先介绍一下 Memory 系统。

真实客服对话往往不是单轮的。用户可能先说"查一下订单 2024060112345"，系统返回信息后，用户再说"那我想换一个"。如果没有记忆，系统就不知道该换哪个订单。

我们的解决方案是用 SQLite 存储三张表：`messages` 保存历史消息，`session_state` 保存会话上下文（最近订单号、最近产品、待补充意图、售后动作），`tickets` 保存售后工单。

当用户第一轮提供订单号时，系统写入 `last_order_id`；如果用户正在退换货但没说清楚换还是退，系统会写入 `pending_intent=return_exchange`。下一轮用户只说"换一个吧"，系统就能沿用上下文，自动创建换货工单。这个设计比只存聊天文本更直接，也更符合工程实现。

## 功能演示（成员 C，约 5 分钟）

下面我来演示系统。先运行 `python3 app.py --port 8000`，打开 `http://127.0.0.1:8000`。

第一个场景是查物流。输入"订单号 2024060112345 到哪了？"。系统识别为 `order_status`，调用 `query_order`，返回商品名、承运方、物流单号和预计送达时间。右侧可以看到工具调用 JSON。

第二个场景是知识库问答。输入"XX 耳机防水吗？能戴着游泳吗？"。系统走 RAG 检索，回答 XX 支持 IPX4，可防汗和小雨，但不建议游泳，推荐 YY 游泳耳机。右侧引用来源显示 `faq.md` 和 `product_xx_airbuds.md`。

第三个场景是退换货。输入"订单 2024060112345 的 XX 耳机左耳没声音，我想换货"。系统创建换货工单，并提示客服会联系用户。这里可以看到 Memory 也在工作，订单号和产品被持久化到会话状态里。

第四个场景是产品对比。输入"XX 和 YY 两款耳机有什么区别？"。系统调用 `compare_products`，从价格、防水、续航和适合场景四个维度对比。

第五个场景是情绪投诉。输入"你们这什么破服务，再不处理我就投诉了！"。系统识别 angry 情绪，先道歉，再触发高优先级转人工。

## 实验设计与评估（成员 D，约 4 分钟）

我负责实验评估和总结。我们做了两组实验。

第一组是 20 条测试对话的全面评估。测试集覆盖查物流、缺少参数、退换货、RAG 问答、追问、工具对比、情绪安抚、闲聊和转人工九个场景。运行 `python3 run_evaluation.py` 后，三项指标都是 100.0%：意图识别准确率 100.0%，工具调用正确率 100.0%，RAG 引用命中率 100.0%。这个结果说明在我们定义的业务范围内，系统能稳定完成路由和工具调用。

当然必须诚实地说，100% 来自自建测试集，不代表真实开放场景也能达到。真实用户会有错别字、口语省略、多意图混合等情况。我们把它理解为"系统在已知场景下功能完备"，而不是"完美泛化"。

第二组是 RAG Top-K 消融实验。我们标注了 8 个问题的正确资料来源，对比 Top-1、Top-3、Top-5。结果 Top-1 命中率 87.5%，Top-3 和 Top-5 都是 100.0%。所以我们默认选 Top-3：比 Top-1 更稳，比 Top-5 更精简。

我们还做了有 RAG 和无 RAG 的对比。如果没有 RAG，系统只能用固定模板回答，像"发票丢了还能不能保修"这种问题就缺少依据。加入 RAG 后，每个回答都能追溯到具体来源，这对客服系统的可信度很重要。

## 总结与改进方向（成员 D，约 2 分钟）

最后总结。SmartCare 完成了一个可运行、可演示、可评估的端到端客服原型。它把课程中的多个知识点串成了一条完整链路：向量检索、RAG 问答、Agent 路由、Function Calling、Memory、情绪识别、评估实验。我们不是单纯调 API，而是把检索、路由、工具和记忆组合成一个能跑业务闭环的系统。

未来改进有三个方向：第一，用 Sentence-Transformers 或 BGE 中文向量模型替换 TF-IDF，搭配 ChromaDB 做持久化向量库；第二，用 Qwen2.5 的 JSON 模式做结构化意图识别，处理多意图和口语表达；第三，接入真实订单和工单后台，增加管理员面板，让系统更接近真实生产环境。
