# 答辩可能提问与回答要点

## 1. 为什么选择题目 8，而不是更常见的情感分析或个人知识库？

题目 8 能覆盖更多课程知识点，包括 RAG、Function Calling、Agent、Memory、Prompt Engineering 和评估。它不依赖 GPU，适合本地稳定演示，同时能做出 Web 界面、工具调用和历史记录，产品完整性更强。

## 2. 你们的系统用了哪些课程知识？

用了词表示与向量检索、RAG、Prompt Engineering、Function Calling、Agent 路由、Memory、结构化输出思想和工程化评估。TF-IDF 是传统向量表示，RAG 是检索增强生成，工具调用对应 Function Calling，多轮状态对应 Memory。

## 3. 为什么没有直接让大模型回答所有问题？

因为客服系统需要可靠的业务动作。订单状态、工单创建和转人工不能靠模型编造，必须调用工具。产品和售后政策也需要引用知识库来源，避免幻觉。因此我们先做意图路由，再决定走 RAG 或工具。

## 4. 为什么默认不用 Sentence-Transformers？

课程演示环境可能无法联网下载模型，所以默认使用标准库实现 TF-IDF，保证可运行和可解释。我们也保留了扩展方向：把 `TfidfVectorStore` 替换为 Sentence-Transformers + ChromaDB，系统其他模块不需要大改。

## 5. TF-IDF 的局限是什么？

TF-IDF 更依赖字面匹配，对语义相近但用词不同的问题召回较弱。例如“泡水运动耳塞”可能不如“游泳耳机”容易命中。后续可以使用 BGE、text2vec 或其他中文 embedding 模型提升语义泛化。

## 6. RAG 为什么选择 top_k=3？

消融实验显示 Top-1 命中率 87.5%，Top-3 和 Top-5 都是 100.0%。Top-3 在召回率和上下文冗余之间比较平衡；Top-5 虽然也能命中，但更容易带入无关片段，影响回答简洁性。

## 7. 你们如何避免模型幻觉？

第一，产品和政策问题先检索知识库，并展示引用来源；第二，低置信度检索时不编造答案，而是提示无法确认或转人工；第三，订单和工单必须通过工具返回结构化结果，不让模型自由生成业务状态。

## 8. 工具调用是怎么实现的？

意图识别后，系统根据路由调用 Python 函数。`query_order` 从模拟订单 JSON 中查物流，`create_ticket` 生成售后工单并写入 SQLite，`transfer_human` 返回人工转接结果，`compare_products` 返回产品参数对比。

## 9. 多轮对话记忆具体保存了什么？

SQLite 的 `session_state` 保存最近订单号、最近产品、待补充意图、最近问题和售后动作。消息历史保存在 `messages` 表，工单保存在 `tickets` 表。这样系统重启后仍能保留历史记录。

## 10. 如果数据量扩大 10 倍，架构怎么调整？

知识库扩大后，应把 TF-IDF 替换为向量数据库，例如 ChromaDB 或 FAISS；文档解析要做增量索引；订单和工单应接入真实数据库；前端历史记录需要分页；评估集也要覆盖更多真实用户表达。

## 11. 系统性能瓶颈在哪里？

当前主要瓶颈是检索和大模型生成。如果启用 Ollama，生成速度受本地 CPU/GPU 影响。知识库较大时，纯 Python TF-IDF 检索也会变慢。优化方法包括向量数据库、缓存常见问题结果、异步工具调用和更小的本地模型。

## 12. 如果用户一句话里有多个意图怎么办？

当前系统主要处理单意图，多个意图时可能优先命中其中一个。改进方案是让 LLM 输出结构化 JSON，把一句话拆成多个任务，例如先查订单，再创建售后工单，并用对话状态逐步确认。

## 13. 评估结果 100% 是否说明系统已经很好？

不能这么理解。100% 是在自建测试集上的结果，说明系统在设定范围内稳定。真实场景会有错别字、口语、省略、多意图和异常订单，需要扩展测试集、引入真实数据，并用人工评分做更严格评估。

## 14. 你们项目最难的部分是什么？

最难的是把“聊天”变成“业务流程”。不只是回答文本，还要判断意图、抽取参数、调用工具、维护上下文、处理情绪和兜底。任何一个环节不稳，用户体验都会受影响。

## 15. 两位成员具体怎么分工？

成员 A 负责选题分析、知识库、RAG 检索、意图识别和实验评估；成员 B 负责 Web 界面、工具调用、SQLite 记忆、后端 API 和演示文档。联调、报告和答辩由两人共同完成。

## 16. 如果老师现场问一个知识库没有的问题怎么办？

系统会尝试检索，若检索分数低就提示当前知识库无法确认，并引导转人工。我们不会让系统编造答案，这也是客服场景中比“看起来会说”更重要的可靠性要求。

## 17. 为什么 Web 页面右侧要展示工具调用和引用？

这是为了可解释性和答辩展示。老师能看到系统内部路由、工具 JSON 和知识来源，判断我们不是写死回答，也不是无依据生成，而是有明确的检索和工具调用链路。

## 18. 后续如何接入真实大模型？

项目已经提供 `LLMClient`，设置 `USE_OLLAMA=1` 和 `OLLAMA_MODEL=qwen2.5:1.5b` 后可调用本地 Ollama。正式环境可替换为 API 调用，并要求模型输出结构化 JSON，以提高意图识别和回答自然度。
